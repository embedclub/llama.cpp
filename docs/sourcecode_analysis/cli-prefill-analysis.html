llama-cli 的 prefill 阶段源码分析

分析对象：tools/cli/cli.cpp（commit 0a2d12fcc）
相关文件：tools/server/server-context.cpp、server-queue.cpp、server-common.cpp、common/common.cpp、src/llama-context.cpp

0. 先给结论

cli.cpp 本身不直接调用 llama_decode()。它复用 server 的推理引擎（server_context / server_context_impl）：

  • cli.cpp 负责：读取用户输入 → 套 chat template 生成 prompt 字符串 → 构造 SERVER_TASK_TYPE_COMPLETION 任务 → 投递队列 → 消费流式结果。
  • 真正的 prefill（prompt 处理） 在 tools/server/server-context.cpp 的 update_slots() 中：把 prompt token 组进 llama_batch，再调用 llama_decode()。
  • CLI 与 server 的唯一区别是任务上打了 task.cli = true，于是服务端在 process_single_task() 里先做一次 CLI 专用 tokenize。

  • 每次最多 n_batch 个 token（逻辑 batch 上限）。超长 prompt 会自动分成多轮 update_slots()，每轮 decode 一批。

  • pos 用 slot.prompt.tokens.pos_next()，对多模态（M-RoPE）也能正确处理位置不连续。
  • common_batch_add()（common/common.cpp:1511）只写指针数组并自增 batch.n_tokens，非常轻量。

阶段 8：整段 prompt 装完 → DONE_PROMPT

tools/server/server-context.cpp:2674-2690（节选）
const auto n_tokens_cur = batch.n_tokens - n_tokens_prev;

    slot.state = SLOT_STATE_DONE_PROMPT;

    GGML_ASSERT(batch.n_tokens > 0);

    // extract the logits only for the last token
    batch.logits[batch.n_tokens - 1] = true;

    slot.n_decoded = 0;
    slot.i_batch   = batch.n_tokens - 1;

    slot.init_sampler();
    SLT_INF(slot, "prompt processing done, n_tokens = %d, batch.n_tokens = %d\n", ...);
}

这是 prefill 与 generation 的分界点：

  • prefill 期间只有最后一个 prompt token 需要 logits（batch.logits[last] = true），其余 token 只更新 KV。
  • slot.i_batch 记录“这个 slot 的 logits 在 batch 中的下标”，decode 之后靠它取结果。
  • 如果 prompt 还没装完（else 分支，2691-2714），状态保持 PROCESSING_PROMPT，下一轮继续。

装批过程中可能顺便创建 KV checkpoint（2731-2733），给后续 prompt 复用 / 投机解码回滚用：

if (do_checkpoint) {

llama_context::decode()（src/llama-context.cpp:1533）内部主要做：

  1. 参数/批次校验，处理 embeddings 输出、backend sampling；
  2. 申请 KV cache 槽位（memory module），必要时做 cache defrag/optimize；
  3. 按 n_ubatch 逐个 process_ubatch()（src/llama-context.cpp:1692）：构建计算图（LLM_GRAPH_TYPE_DECODER）、调度 ggml 后端执行、把 K/V 写回 llama_memory、按 batch.logits 把需要的 logits 写入输出缓冲；
  4. 失败时回滚对应位置的 KV，并返回错误码。

对 prefill 来说，这里就是“一次性把这段 prompt 的 KV 算出来”。

prefill 的进度判定

slot.prompt.n_tokens()   // 已处理的 token 数
slot.task->n_tokens()    // 目标 prompt 总 token 数

两者相等 → prefill 结束；否则下一轮 update_slots() 继续。不要把 batch.n_tokens 当成 prompt 总长度，它只是当前这一批的大小。

时序总览（单轮对话）

用户输入 │ ├─ cli.cpp: format_chat() → prompt 字符串 ├─ cli.cpp: post_task(COMPLETION, cli=true) │ └─ 推理线程 server_queue::start_loop() │ ├─ process_single_task() │ ├─ tokenize_cli_input() → task.tokens │ └─ launch_slot_with_task() → state=STARTED │ └─ update_slots() ├─ STARTED → PROCESSING_PROMPT ├─ cache_prompt: get_common_prefix() → n_past ├─ 填 batch（≤ n_batch 个 token/轮） ├─ 装完 → DONE_PROMPT，logits[last]=true ├─ llama_decode() → llama_context::decode() → process_ubatch() └─ 采样首 token → GENERATING → 流式返回 │ └─ cli.cpp: rd.next() 打印 content_delta / timings

调优参数（与 prefill 直接相关）

参数影响
-b/--batch-size（n_batch）每轮最多处理多少 prompt token；越大 prefill 轮数越少，但显存峰值越高
-ub/--ubatch-size（n_ubatch）真正图执行的物理批；影响单次 kernel / 显存占用
--cache-prompt / cache_prompt是否复用历史 prompt 的 KV（多轮对话提速关键）
--cache-reuse N（n_cache_reuse）旧 KV 片段平移复用（中间相同、结尾不同时有效）
--no-context-shift影响上下文满时的截断策略（prefill 前会检查）
--swa-full / n_ctx_checkpoints与 SWA checkpoint 恢复相关
-np/--parallel、--cont-batching多 slot 时能否把多个 prompt 合并进同一批 prefill

一句话总结

cli.cpp 的 prefill 不是本地循环，而是“把 chat 模板渲染成字符串 → 打成 COMPLETION 任务 → 由 server_context 的 update_slots() 做 prompt 装箱 → llama_decode() 一次性算完 prompt 的 KV → 只取最后一个 logits 采首 token”。理解这条链的关键分界点是 SLOT_STATE_DONE_PROMPT 和 batch.logits[last] = true。
本文基于仓库当前 commit 0a2d12fcc 生成。行号可能随上游迭代变化，检索时优先按函数名（generate_completion、process_single_task、update_slots、launch_slot_with_task）定位。
